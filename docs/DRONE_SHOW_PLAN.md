# Drone-show mode: implementation and production plan

17 September 2026. First delivery: a camera-free browser choreography simulator in the existing editor. Target: usable on PC, tablet and Android browsers, with physical S9+/S22 Ultra performance still to be measured.

## Product and researched workflow

Turn drawing strokes into aerial light formations. A storyboard combines formations, movements and LED cues; a player makes the result easy to inspect from the audience and from the side. The built-in **Demo** plays takeoff → robot → fish → Eiffel Tower → drone-light fireworks → return and landing. **Replay my drawing** samples the current scene's stroke centre lines and colours into an additional performance. Editing data stays intact.

[Skybrush's design tutorial](https://docs.skybrush.io/public/skybrush-studio-for-blender/latest/tutorials/easy-drone-show-design.html) separates formation design, movement, lighting and validation. We adopt that separation. [Its storyboard reference](https://docs.skybrush.io/public/skybrush-studio-for-blender/latest/panels/formations/storyboard.html) uses timed formations and explicitly distinguishes takeoff, performance and landing. [Skybrush Studio](https://skybrush.io/modules/studio/) also exposes altitude, speed, acceleration and proximity analysis. These references inform our design; no third-party choreography or assets are copied.

## Implement now

1. **Deterministic show model:** 256 stable virtual drone IDs, a launch grid, sampled vector formations, a timed cue sheet, distance-based assignment between formations, smooth endpoint motion and independent LED cues. Every drone follows a continuous path and returns to its own launch location. Lights fade out before a normal formation transfer and reveal only at the next formation. Fireworks are moving light formations, not pyrotechnics or spawned particles replacing drones.
2. **Replay renderer:** reuse the existing WebGL renderer with a separate show scene/camera. Render batched light points, dim drone markers, an optional bounded trail buffer and a simple night stage. No shadows, post-processing or imported 3D assets required. Blender is optional for future designer-authored formations.
3. **Demo UX:** visible Demo button; a dedicated stage with cue list, phase/time feedback, pause/resume, restart, seek, playback speed, front/orbit camera and trail toggle. Pause when the tab is hidden. Exit restores the editor and its drawing/view/history. Do not overwrite the project or place hundreds of entities in the drawing document.
4. **Drawing-to-show:** sample world-space stroke paths by length, including curved-sheet deformation. Keep source colours and relative depth, normalize them into a preview stage, and distribute the fixed fleet along the paths. Explain that paper, images, blocks, stroke width and brush effects are not formation inputs yet. Empty/degenerate drawings get a clear message.
5. **Review and focused checks:** stable identities/count; endpoint and cue continuity; LED timing; finite positions; deterministic seeking; pause/background handling; landing; editor preservation; mobile layout and bounded draw calls. Run the normal web checks and a focused browser replay, without a broad physical-flight test campaign.

## Boundaries and design review

The current four-metre drawing format remains unchanged. Show preview coordinates are a separately normalized virtual stage; exported drawing JSON is still artwork, not a flight mission. This increment has no camera, IMU, radio, real drone connection or native Android show player. Simulated timing is chosen for a short demonstration. Assignment and smooth interpolation improve visual continuity but do not prove collision-free or physically feasible flight. The stage labels this mode **Simulation**.

## Implemented result

Web Studio 09 includes **Demo** above the canvas and **Replay my drawing** in the inspector. The built-in timeline lasts **87 seconds** at 1×: launch grid 0–2, takeoff 2–8, robot assembly 8–15 and display 15–23, fish transfer 23–30 and display 30–38, Eiffel Tower transfer 38–45 and display 45–54, firework launch 54–61 and burst 61–70, return 70–77, landing 77–85, landed 85–87. Cue buttons seek to a representative moment and pause. A custom drawing replaces the three figure cues with one 12-second display, then fireworks and landing.

The player supports 0.5×, 1× and 2× speed; Play/Pause, Restart, timeline seeking, Trails and Front view. Drag/pinch/wheel orbit controls work while paused or playing. Esc and Back to drawing leave the mode. Hiding the tab pauses it; the user resumes explicitly. Seeking recalculates positions and trails from show time, so playback history does not change the result. No audio is included.

## Code and logic review

- **Identity and landing:** every formation has exactly 256 samples. A deterministic Hungarian assignment minimizes squared travel distance and preserves the correspondence of target colour and position. A drone keeps its ID across all cues and returns to its own grid coordinate. There are no replacement particle fleets during fireworks. Matching is not a flight-separation solver; coincident outline samples and crossing paths still require the production planning/validation gate above.
- **Motion and lighting:** quintic easing gives zero endpoint velocity and acceleration for the interpolated transfers. Transfers hold their departure position while fading the old LEDs, move with LEDs off, and reveal the new colours only after arrival. Fireworks intentionally move while lit. The burst pulse was tapered at its boundary to keep colour continuous into return. Takeoff/landing row delays finish within their scheduled interval.
- **Drawing conversion:** use stroke centre lines, convert attached points through the actual curved parent transform, and clip them to the sheet's visible rectangle. Rejoin contiguous clipped segments before length-based sampling so a heavily sampled stroke does not acquire extra drones just because it had more input points. RGB colour and relative depth are preserved; placement/scale are normalized to the virtual stage. A stroke-only scene with no drawable length reports an error before entering show mode. Paper visibility does not delete ink.
- **Editor isolation:** the authored entities, selection and history are not replaced. The player has its own Three.js scene, camera and OrbitControls; the original controls and hidden editor panels are disabled during replay. Exit restores the UI. Editor pointer/keyboard handlers are gated while the show owns the canvas. Stale editor toasts are cleared on entry.
- **Performance and cleanup:** one existing renderer, reused typed buffers, batched points, one trail line batch, instanced skyline and a cached built-in show. Target at most 30 animation renders/second; paused playback renders only on interaction. A small timestamp tolerance avoids undershooting the intended cap on 60 Hz displays. No per-drone meshes, physics engine, shadows, post-processing or image downloads. Exit disposes controls, geometries, materials and the skyline's instancing resources. Planning is synchronous for this small fixed fleet; worker planning remains necessary before increasing fleet size substantially.
- **Mobile framing:** reserve visual space for timeline controls, fit the stage to portrait width and retain 44 px primary controls. The mode does not request a camera or motion-sensor permission. Reduced-motion users initiate playback explicitly and have pause/seek controls; automatic camera movement and flashing/strobe effects are absent.

## Focused verification

31 web unit tests pass, including all existing editor logic and four show checks: stable fleet/finite positions/home landing, trajectory and LED continuity at cue boundaries, deterministic assignment, curved/hidden-sheet sampling and clock semantics. Production web build passes.

The focused Chromium flow verifies automatic Demo progress, pause, completion/replay, speed/restart, formation seeking, LED-off landing, orbit/front view, a synthetic visibility-change pause, 412 × 915 layout, replay of curved drawing ink, repeated entry/exit and unchanged export/history after both replay modes. Screenshots of robot, fish, tower, fireworks, landing and mobile were inspected. No browser errors were reported. The synthetic background event checks app behavior, not every browser's operating-system suspension policy.

No native code or project format changed, so no additional Android build was needed. Physical-device frame rate, thermal/battery behavior, full-duration browser soak, continuous collision checking and real-aircraft feasibility remain unverified. The performance targets in the roadmap remain targets.
